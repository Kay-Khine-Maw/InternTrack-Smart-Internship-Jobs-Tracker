## 3. What I learned

I learned that a green exit code is not always evidence. `npm run test:extract` exited 0 while `verify-extract.ts` was empty, so it did not prove extraction, missing fields, or provider failure. QA has to report what the command actually checked.

I also learned to record failures honestly. The matching script failure (`100 !== null`) and the sixteen `tsc` errors stay in the measurement file and issue log instead of being hidden. That gives the team clear follow-up work and keeps demo claims limited to what was proven.

Finally, I learned that UAT completion and timed before/after studies are different. Moderated sessions can show tasks completed while duration is still “not measured.” A test plan that mixes those without labels overstates the evaluation.

## 6. Reflection

### 6.1 Lessons learned: How did building the app with AI affect software engineering?

Building InternTrack with AI made it easier to draft test ideas and documentation, but QA still had to run commands and write down actual output. AI could suggest cases; it could not turn an empty verify-extract file into proof.

I also learned that AI-built features need ordinary regression discipline. Matching, extraction, and TypeScript checks failed or were incomplete on the recorded date even though the product uses Gemini elsewhere. Software engineering quality still depends on reproducible scripts, issue logs, and refusing to mark the release Accepted without evidence.

### 6.2 Where do I stand in the software industry today, in the AI era?

I see myself as a QA engineer who must keep foundations strong enough to challenge both the product and AI-written tests. Without that, I might accept a passing script that asserts nothing. In the AI era, my value is making environment, limits, and failures visible next to every claim.

### 6.3 What is my plan for next year and the next five years?

Next year I want to tighten automated checks so extract and matching scripts assert real behavior, and to plan timed measurements when the team runs UAT again. I also want clearer issue-log habits tied to each failed command.

Over five years I hope to grow into a quality engineer who can lead verification for AI-assisted products — fast enough to keep up with delivery, careful enough that every PASS line means something a reviewer can trust.
